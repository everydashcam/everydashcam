# SEO and URL structure

Operational runbook for search-engine optimization and the multi-locale URL layout.
`CLAUDE.md` keeps only the two rules that touch day-to-day code (extension-less URLs,
git-mtime `lastmod`); the procedures, rationale, and engine-specific quirks live here.

## URL structure and root redirect

All locales (including English) live under `/<lang>/` - there is no "default locale at /" shortcut. The structure:

- `/` - **redirect stub**, no content. Canonical and instant meta refresh point to the current host's fallback locale (`/en/` on primary, `rootLocaleSegment` on mirror). Production has no robots noindex; staging and mirror canary retain noindex. The inline bootstrap picks a saved or browser language and navigates within the current host. Roots are excluded from hreflang and sitemap.
- `/en/`, `/ru/`, `/de/`, ... - regular locale homes with full content, `<link rel="canonical" href="/<lang>/">` self-referencing.
- `/en/cameras/<slug>/`, `/ru/cameras/<slug>/`, ... - per-locale vendor pages.
- `/cameras/<slug>/` (legacy) - server-side 301 to `/en/cameras/<slug>/` via `dist/_redirects` (generated by `vite-plugins/redirects.ts`). CF Pages applies these on the edge - NOT Functions, just a static config file.
- `/<lang>/privacy/`, `/<lang>/terms/`, `/<lang>/add-my-camera/` - single-language documents generated from existing translations in `public/*.html`. The old extension-less addresses remain locale-selection stubs on the current host, outside hreflang and sitemap.
- `hreflang` describes the translations actually published for each page, including the page itself. `x-default` is the primary English version of that same page. Primary Portuguese retains both `pt` and `pt-BR`; Simplified Chinese uses `zh-Hans`, without a generic `zh` alias. Regional deployments add a separate language/region code for each mirror URL. HTML and sitemap carry the same graph through `vite-plugins/seo-alternates.ts`; visible navigation stays on the current host.

Share-link contract: any URL with an explicit locale segment is **share-safe**. URL always wins over localStorage/navigator (URL-first detection in the bootstrap and in `detectInitialLang`). A Russian user sharing `/ru/cameras/70mai/` lands every receiver on Russian, regardless of their browser language. The lang-suggestion banner (`src/ui/lang-suggestion-banner.ts`) offers a one-click switch when the receiver's `navigator.language` doesn't match the URL locale - dismissable for the current page view (dismissal scope lives in `src/ui/lang-suggestion-banner.ts`).

The `/` redirect logic on the **client** is deliberate: a static `_redirects` line for `/` could only pick one locale unconditionally - which defeats the priority chain. The trade-off: GoogleBot without JS sees `<meta refresh>` to `/en/` and the canonical link - that's enough to consolidate ranking signals onto `/en/` and reach all other locales via the sitemap + hreflang graph.

Source of truth for the locale list, URL segments, hreflang codes and `og:locale` mappings is `src/i18n/seo-config.ts` `SEO_LOCALES`. Adding a locale: append an entry there + dictionary file + a `BANNER_COPY` entry in `src/i18n/banner-copy.ts` (the file's header carries the why; `banner-copy.test.ts` fails on drift from the dictionaries).

## Regional deployment profiles

The build-time policy lives in `vite-plugins/deployment-profile.ts`. Runtime
locale selection does not read private deployment configuration. Export these
variables in the build process; unprefixed variables in a Vite dotenv file do
not populate `process.env`.

| Configuration | Search policy |
| --- | --- |
| No mirror configuration | Ordinary primary-only site |
| Mirror profile without `SEO_CUTOVER=1` | Crawlable noindex canary, primary canonical URLs |
| Cutover without `regionalHreflangs` | Legacy single-owner locale policy, retained for coordinated migration |
| Cutover with `regionalHreflangs` | All published languages indexable on both hosts, self-canonical URLs and a shared regional graph |
| `VITE_NO_INDEX=1` | Global staging noindex overrides the production policy |

`SEO_MIRROR_CONFIG` contains `origin`, `localeSegments`, `rootLocaleSegment`,
and an optional `regionalHreflangs` map. In regional mode, both the locale list
and map must cover every indexable locale in `SEO_LOCALES`. The map keys match
the locale URL segments; values match their language and script and add a
region. Codes must be unique across the complete graph, including primary
aliases. Adding a project locale without a regional pair fails the build.

Synthetic configuration example, targeting a test region:

```json
{
  "origin": "https://mirror.example.test",
  "localeSegments": ["de", "en", "es", "fr", "ja", "ko", "pl", "pt", "ru", "zh"],
  "rootLocaleSegment": "de",
  "regionalHreflangs": {
    "de": "de-CH", "en": "en-CH", "es": "es-CH", "fr": "fr-CH",
    "ja": "ja-CH", "ko": "ko-CH", "pl": "pl-CH", "pt": "pt-CH",
    "ru": "ru-CH", "zh": "zh-Hans-CH"
  }
}
```

Build both profiles from the same revision with the same map and
`SEO_CUTOVER=1`, changing only `DEPLOYMENT_PROFILE`. Each sitemap lists only
its own host's indexable URLs. Canonical, OG URLs, structured data and
breadcrumbs describe the current regional page. Production regional pages
have `max-image-preview:large` and no general or engine-specific noindex.
Keep `robots.txt` crawlable and its `Sitemap` line pointed at its own host.
Staging and canary also allow crawling so robots can see their noindex meta
and `X-Robots-Tag` header. Technical noindex pages retain their own policy.

Validate saved artifacts together:

```sh
npm run check:seo -- /path/to/primary /path/to/mirror
```

`npm run test:seo-regional` builds and checks a synthetic production pair;
CI runs it alongside the canary checks. A single-artifact check cannot confirm
the other host's content. The paired check identifies pages by full URL so
the same path on two hosts remains two distinct pages.

Publish the validated pair through the [release runbook](deploy.md), with a
coordinated configuration switch. Avoid leaving one host advertising a graph
the other does not publish. Actual mirror settings stay private. After release,
check live HTML, response headers, robots and sitemaps on both hosts. Submit
each host's own sitemap; for IndexNow set `INDEXNOW_ORIGIN` and its matching
ownership key and read URLs from that host's live sitemap.

Regional annotations are search hints, not per-user routing or a guarantee
that every result uses one host. Search engines may select a different
canonical or regional URL. Monitor several page families, languages, regions
and engines after recrawling, including direct results as well as webmaster
reports. See Google's [localized-page guidance](https://developers.google.com/search/docs/specialty/international/localized-versions)
and [multi-regional guidance](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites).
HTML alternates are required: [Yandex no longer uses sitemap entries for language relationships](https://yandex.ru/support/webmaster/en/yandex-indexing/locale-pages).

## Localized documents

Document generation preserves the existing translated body text and publishes
only available translations, with localized titles and descriptions. An explicit
locale URL determines the document language even when `?lang=` or a saved
preference disagrees. Language selection navigates to the same document's
locale path on the current host. Links to the English legal text point to its
English path.

Old `/privacy`, `/terms`, and `/add-my-camera` links select a document using
`?lang=`, saved preference, then browser language, with a stable fallback for
no-JavaScript clients. They remain transition URLs rather than separate language
versions. `public/doc-lang.js` still supports standalone pages such as 404.
Document HTML stays outside the service-worker precache; hosting must serve
its directory indexes rather than the app shell.

## Search-engine SEO

Target queries: "dashcam player / viewer", "&lt;vendor&gt; player", and localized variants. Top engines across locales: Google (most locales), Bing (long tail + AI surfaces: Copilot, ChatGPT browse, DuckDuckGo, Brave, Yahoo non-JP), Yandex (RU), Naver (KO), Baidu (ZH, with constraints).

**What's wired in.** Static prerender covers locale homepages, camera and alternative catalogs and their pages, feature/guide pages, and localized documents. Current families and translations are defined in the generators linked below. Indexable pages use the deployment policy above for canonical and alternates, with matching page metadata and structured data. `sitemap.xml` carries `xhtml:link` alternates. URLs with independently trackable source files also get a real `<lastmod>` derived from `git log -1`; programmatic page families whose locale and slug content shares monolithic files omit it because a shared file mtime cannot identify which URL changed. CF Pages builds from a **depth-1 clone**, where `git log -1 -- <file>` does NOT fail - it answers HEAD for every tracked file, stamping every dated URL with the deploy's commit time. `git-mtime.ts` detects the shallow clone, runs `git fetch --unshallow` once per build, and omits `<lastmod>` entirely when the fetch fails. After changing anything in that area, verify that every emitted date belongs to an independently trackable URL source.

**Extension-less URLs.** See `CLAUDE.md` → SEO. Cloudflare normalizes HTML paths; advertise the final destination to keep sitemap, canonical and internal-link signals consistent. A redirect alone does not explain Search Console's "Discovered - currently not indexed" status: inspect the URL and Google's selected canonical before diagnosing it.

**Webmaster verification.** Google + Yandex via DNS TXT (records live in the registrar, no in-repo trace). Bing supports the same DNS TXT / CNAME approach. Naver verification is intentionally skipped (Naver supports only a meta tag / HTML file, no DNS TXT). Baidu intentionally skipped: mainland China is unreachable from Cloudflare Pages without an ICP license, and Baidu downranks non-ICP sites; realistic `/zh/` audience is Taiwan / Hong Kong / Singapore / diaspora, where Bing and Google dominate.

### Google verification after deployment

Run the build before publishing. For an existing build directory, run `npm run check:seo`; its checks live in `scripts/check-seo.mjs`.

- In Search Console, inspect a homepage and a page from each changed SEO family. Compare fetched HTML, rendered content, indexing eligibility, and Google's selected canonical. Repeat for affected languages and both regional hosts. See [URL Inspection](https://support.google.com/webmasters/answer/9012289).
- Submit each host's own sitemap and monitor indexing exclusions. Sitemap submission is discovery, not an indexing guarantee. See [Google's sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).
- Validate representative published pages with [Rich Results Test](https://search.google.com/test/rich-results). Markup must describe visible content. Never add invented reviews or ratings to qualify for a software result; valid schema alone does not guarantee an enhanced result. See [structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).
- Compare mobile and desktop field data in [Search Console's Core Web Vitals report](https://support.google.com/webmasters/answer/9205520). Use lab tests to diagnose loading and layout problems; a local pass does not establish real-user LCP, INP or CLS.
- Compare impressions, clicks and CTR by query, page, language and device over comparable periods in the [Performance report](https://support.google.com/webmasters/answer/7576553). Use observed demand to improve distinct, useful pages; do not expand near-identical keyword pages to increase URL count.

Check a nonexistent production URL returns HTTP 404, and legacy URLs redirect to their intended destinations. Cloudflare's [top-level 404 page](https://developers.cloudflare.com/pages/configuration/serving-pages/#not-found-behavior) handles misses; `_redirects` [does not support 404 rewrites](https://developers.cloudflare.com/pages/configuration/redirects/#advanced-redirects).

### IndexNow

How the protocol works: we generate an arbitrary 8-128 char key ourselves (no console-issued token from any engine - IndexNow is unregistered push, not webmaster verification). Proof of ownership: a file at `https://everydashcam.app/<KEY>.txt` whose body is the same key. When we POST a submission, we include `key` and `keyLocation`; IndexNow servers fetch the keyLocation, compare bodies, and either accept or reject. The key is NOT public: the spec says only you and the engines should know the key and its location. The file is served but never linked - it must stay out of the sitemap, robots.txt, the repo, and the SW precache allowlist (`vite-plugins/sw-precache.ts`), or anyone can spam IndexNow on the domain's behalf until engines throttle the key.

Where the key lives: the `INDEXNOW_KEY` GitHub Actions secret and nowhere else - the production build (the `deploy` job of `release.yml`) feeds it to `vite-plugins/indexnow-key.ts`, which emits `dist/<KEY>.txt`, and the ping reads the same secret. Deliberately in no file, not even `.env.example`: the repo carries zero trace of the value. The ping script pre-flight-checks the live keyLocation before submitting, so the baked file and the secret drifting apart (a half-deployed rotation) fails with one clear message instead of five opaque 403s.

Day-to-day usage: automatic. The `ping` job of `.github/workflows/release.yml` runs after the production deploy job of the same `v*` tag run (a push to `main` only deploys staging, which must never be pinged) and calls `scripts/indexnow-ping.mjs`, which fetches the **live** `https://everydashcam.app/sitemap.xml` (what is deployed is what gets pinged) and POSTs every `<loc>` directly, in parallel, to each IndexNow engine in the `ENGINES` list of `scripts/indexnow-ping.mjs` (which also records why Amazon is skipped). The batch (grows with every new page family) is well under the per-request limit (10000) for every engine. Ad-hoc ping without a deploy: the manual run button of `.github/workflows/indexnow.yml` (workflow_dispatch), or locally `INDEXNOW_KEY=<key> npm run indexnow`.

**Why direct instead of `api.indexnow.org`.** We POST each engine directly rather than the global fan-out endpoint: it gives per-engine visibility (the script logs HTTP status per engine, so a Naver 422 or a Yep 5xx is obvious rather than silent), and the global endpoint's documented fan-out does not reliably reach Bing for this host, while a direct POST to the engine's own endpoint does. Exit code is 0 if at least one engine accepted; only a full sweep failure (everyone 4xx/5xx, or no network) exits 1.

Re-pinging unchanged URLs on every deploy is fine - individual engines may 429 once in a while; the script treats 429 as a per-engine soft pass (warns, keeps going, counts as accepted for exit-code purposes).

Rotating the key (if disclosed - e.g. it leaked into a commit or a log):
1. `openssl rand -hex 16` - generate a new value.
2. Replace the `INDEXNOW_KEY` GitHub Actions secret.
3. Redeploy production (a new tag). The chained ping uses the new key automatically; the old file 404s after the deploy, which is fine - only the current key needs to validate. The ping's pre-flight catches a half-done rotation (secret updated, prod not redeployed).

Engines other than the IndexNow five use their own channels: Google via Search Console + sitemap auto-discovery (no IndexNow); Baidu is intentionally unreached (see Baidu note above).

### Crawler fallbacks

**`<noscript>` fallback** in `index.html` body: page.title + meta.description (translated by prerender like other `data-i18n` elements) + brand links + continue link. Read by JS-disabled crawlers (Baiduspider, Yetibot/Naver, Yandex with JS rendering disabled in Webmaster) and by users with JS off.

**llms.txt** at `dist/llms.txt` for Anthropic / Perplexity / ChatGPT-search. Google's docs state it outright (ai-optimization guide): llms.txt is not needed for Google Search and does not affect visibility either way - it stays purely for the non-Google consumers. Built by `vite-plugins/llms-txt.ts`.

### Out of scope

Google `Indexing API` (closed to non-JobPosting / non-BroadcastEvent). Google `FAQPage` and `HowTo` enhancements: keep existing semantic markup consistent with visible content without promising a search feature. Yandex `Turbo Pages` (deprecated). Baidu `MIP` (deprecated). `WebSite + SearchAction` (no internal search). `meta name="author/publisher"` (ignored by all majors). `meta name="keywords"` (Google states it is not used in ranking, modern Yandex/Bing ignore it too - pure head noise). `X-Robots-Tag` on production (production indexing is controlled via `robots.txt` + `canonical`; staging builds DO emit `X-Robots-Tag: noindex` via `_headers` + per-page noindex meta, with robots.txt deliberately ALLOWING crawl so the noindex is visible to crawlers - see `SeoBuildOptions` in `vite-plugins/seo-prerender.ts`).
